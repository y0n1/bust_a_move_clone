## Highlights

### 1. The icon and manifest defect is closed (#95, PR #97)

The one change in this release a player can see.

- **What players saw at `v1.0.0`:** a broken favicon and install icon, one
  failed request on every page load, and no "Install app" prompt. The four
  icon files were served as base64 **text**, and `manifest.json` declared
  `icons/Icon-maskable-512.png`, a file that never existed.
- **What ships now:** the four files are real PNGs, the dangling manifest
  entry is gone, and the deprecated `apple-mobile-web-app-capable` meta tag
  is replaced.
- **Why it cannot quietly come back:** `test/web_assets_test.dart` (added by
  the fix) asserts a real PNG signature on every icon and a manifest with no
  missing entries. It fails **3/3 on `6c21684`**, so `v1.0.0` would fail
  this suite.

### 2. Every deploy now verifies the live site (OPS-4, #82, PR #99)

A green deploy job only proved that Pages accepted an artifact. It said
nothing about what a visitor gets, and post-deploy verification was a manual
checklist that was easy to skip — and, when it was run, blind.

`deploy-pages.yml` gained a `smoke` job that runs
`test/quality/post_deploy_check.py` against the **live URL** the moment
`deploy` succeeds, and fails the run when the site is unhealthy:

| # | Check | Proves |
|---|-------|--------|
| 1 | Site root returns `200` with an HTML content type | Pages serves the app, not an error page |
| 2 | `version.json` returns `200` and matches the release | The deploy served the artifact we built |
| 3 | `manifest.json` `200`; every declared icon plus `favicon.png` `200` **with a real PNG signature** | The #95 defect class is covered |
| 4 | Headless Chrome boots Flutter, the semantics tree appears, the start screen renders and **PLAY** is reachable, no blocking console errors | A player can start a game |

Check 3 exists because check 4 structurally cannot see it: browser-level
manifest and image fetches never reach the page's CDP console session, which
is exactly how #95 reached production while the smoke suite reported 10/10.
Every network assertion retries with backoff until `--wait` elapses, so a
slow CDN edge does not flake a release. Exit codes: `0` pass, `1` a named
check failed, `2` the tool could not run.

### 3. Rollback without a revert (OPS-2, #80, PR #100)

Previously, a broken production meant merging a revert PR before anything
could be done. `deploy-pages.yml` now accepts `workflow_dispatch` with a
**required `ref` input**, so a known-good commit, tag, or branch can be
deployed without touching `main`. Manual runs stay distinguishable from push
runs (`run-name` → `MANUAL deploy of <ref> — <reason>`, a **Deploy source**
table in the run summary, and a `::warning title=Manual deploy::` annotation
on dispatch only), and privileges stay least-privilege (`pages: write` on
`deploy` only). See [Rollback](#rollback).

### 4. One toolchain, and it cannot drift (OPS-1, #79, PR #93)

`subosito/flutter-action` was configured with `channel: stable`, which
resolves whatever is current at run time: two runs of the same commit could
use different SDKs, and a Flutter release could turn a previously green build
red with no code change. Flutter is pinned to **3.47.1** in both workflows,
declared **once** as a workflow-level `FLUTTER_VERSION` that both CI jobs
read — copying it into each job would let a bump update one and leave the
other on a different toolchain. The bump procedure is documented in
`docs/ops/deployment.md` § *Bumping the toolchain*.

### 5. The web bundle is built before merge (OPS-3, #81, PR #94)

Nothing built the web bundle on the PR gate: the deploy workflow did, but
only *after* a push to `main`. A base-href typo or a web-only compile error
therefore reached players before anyone saw it. `ci.yml` gained a `build-web`
job running the **byte-identical** production command
(`flutter build web --release --base-href /bust_a_move_clone/`), in parallel
with `analyze-test` so no PR pays the build time twice, plus a bundle-size
table (on-disk and gzip) in the job summary.

### 6. The release smoke path is one command (QE-1, #69, PR #96)

`test/quality/release_smoke.py` builds the artifact, stages it under a
`bust_a_move_clone/` directory so the Pages base href resolves, serves it,
and drives headless Chrome over the DevTools Protocol through the **ten
critical-path steps** of `docs/quality/test-strategy.md` §9.

```bash
python3 test/quality/release_smoke.py          # builds, then drives the app
python3 test/quality/release_smoke.py --no-build
```

Zero third-party dependencies, and deliberately no `chromedriver`,
`flutter drive`, or VM service — none of which are available for a release
CanvasKit build. State is read the way a player sees it (Flutter's semantics
tree; the canvas-painted overlay headline by its `aria-label`), never by
reaching into the app.

### 7. Players actually receive new builds (QE-8, #76, PR #102)

The task asked for service-worker update tests. Measuring first showed there
is **no caching service worker to test**:

- `build/web/flutter_service_worker.js` is 784 bytes — it calls
  `skipWaiting()`, then **unregisters itself** on activate and reloads its
  clients. It caches nothing.
- GitHub Pages serves **every** asset — `index.html`, `main.dart.js`,
  `version.json`, and the service worker itself — with
  `cache-control: max-age=600`.

So the path that decides what a player sees is the plain HTTP cache, and
that is what `test/quality/sw_update_check.py` tests: it stages the real
`build/web`, serves it with Pages' headers, publishes build B mid-session
(rewrites `version.json`, appends a marker to `main.dart.js`), and asserts
the outcome. Method and measurements are in `docs/quality/sw-update.md`.

**Consequence for players, and the reason #101 exists:** a player with the
tab already open can keep playing the previous build for **up to ten
minutes** after a deploy, with no prompt. Changing the service-worker
strategy was out of scope for the task; the reload-prompt proposal is
[#101](https://github.com/y0n1/bust_a_move_clone/issues/101).

### 8. Defects arrive with a failing test (QE-10, #78, PR #105)

`docs/quality/bug-regression-template.md` landed in #92, but nothing linked
to it, so nothing made it the default — and the issue was never really about
the file. Now:

- Linked from `docs/quality/test-strategy.md` (companions block + §12). The
  repo has no `PULL_REQUEST_TEMPLATE`, so that link target is stated rather
  than silently skipped.
- **Proved on a real defect, not a sample.** The subject is D2 (see
  [Known issues](#known-issues)): a probe test was written and run against
  `develop`, and it failed for the named reason — `28 320` is exactly
  `16 × (0+1+…+59)`, so the failure message alone identifies the cause. The
  probe was then **deleted**, because a test that fails on `develop` belongs
  in its fix PR, not a documentation change.
- The trial closed five gaps in the template, including a **Clock and tick
  rate** item in §4 (a seed does not reproduce a time defect) and a
  **Harness** line in §2 (naming a perfect assertion is useless if the fixer
  cannot run it).

### 9. The engine is provably deterministic (#106, PR #107)

- **Value equality** for `Bubble`, `Projectile`, and `GameState`
  (`lib/game/model.dart`) so engine snapshots can be compared wholesale,
  using `collection`'s `DeepCollectionEquality`.
- **`test/engine_determinism_test.dart`:** same-seed initial states are
  equal, identical shoot/tick sequences produce identical states, and a
  50-step level-2 replay is reproducible.
- *Player relevance (inference, not a shipped feature):* a seeded engine that
  replays identically is the precondition for daily challenges, shareable
  replays, and fair async play — and it means engine tests stop being able
  to flake.
- Same PR consolidates team guidance (`AGENTS.md`, `docs/agent-team.md`,
  `docs/architecture.md`, a new `CONTRIBUTING.md`, the role files) and
  git-ignores `.mcp.json`, which may hold a local API token.

### 10. The honest shot score is specified, not shipped (UX-2, #68, PR #103)

`docs/design/specs/honest-shot-score.md` is an implementation-ready spec for
PB-01, the top-ranked product feature. **Nothing in the game changed** — the
spec is the input to the implementation task. It documents two independent
defects (D1 and D2 below) and the acceptance criteria that will pin them,
including AC-9 (linear FX clock, regression for D2).

> **PM follow-up, recorded rather than hidden:** PR #103's body cites "#66"
> as PB-01's implementation task. That reference is wrong — #66 is PM-3 (the
> backlog task) and is still open. No PB-01 implementation issue exists on

### 11. Dependency updates and a supply-chain gate (OPS-7, #85, PR #104)

Before this, dependencies updated **by accident**: nothing scheduled a bump and
nothing could say "no" to a new third-party package for a reason that has
nothing to do with our own code.

- `.github/dependabot.yml` — weekly updates for the two ecosystems this project
  actually has, `pub` and `github-actions`. Minor and patch bumps arrive
  grouped (one PR per ecosystem per week); **majors arrive alone**, because a
  major is a decision and should not be buried in a five-package routine PR.
  GitHub Actions is the load-bearing half: it is pipeline code we did not write
  that runs with a repository token.
- `.github/workflows/dependency-review.yml` — fails a PR that *introduces* a
  known-vulnerable dependency, at `fail-on-severity: moderate` for runtime
  scopes. `moderate` rather than the action's `low` default is deliberate: a
  low-severity advisory in a dev-only transitive package turns PRs red often
  enough that people re-run until green, which is worse than no gate.
  `show-patched-versions` answers the only question anyone asks when it fails.
- `docs/ops/dependencies.md` records the cadence, the triage steps, and —
  unusually for a repo doc — **what the gate does not cover**: the Flutter and
  Dart SDKs (pinned by `FLUTTER_VERSION`, invisible to pub resolution), runner
  OS packages on a moving `ubuntu-latest` image, advisories already present on
  the base branch (the action diffs two revisions, so an unchanged package
  produces no diff and no failure — that is what Dependabot *alerts* are for),
  and licences (the check is on, but there is no allow-list, so it cannot fail
  today; adding one is a policy decision, not a switch).
- **Honest timing:** `dependabot.yml` is read from the **default branch**, so
  this file is inert until the release carrying it reaches `main`. The first
  real proof of the automation is the first Monday after this release ships,
  not the day it merges. A malformed file also fails *silently* — no PRs, no
  red workflow — so it is validated before merge, as the file's own header
  instructs.

### pubspec and the build number

This PR does **not** touch `pubspec.yaml`, mirroring the `v1.0.0` precedent
exactly (PR #98 changed five docs files and no manifest). `pubspec.yaml` on
`develop` still reads `1.0.0+1`; the bump to **`1.1.0+1`** belongs on
`release/1.1.0`, which is where the artifact's version is fixed (release
procedure, step 3).

> **Do not cut and deploy with `pubspec.yaml` still at `1.0.0+1`.** Check 2
> of `post_deploy_check.py` compares the live `version.json` against that
> file's `version:` field, so a missed bump makes the smoke job report
> **green** while production announces the *previous* release — precisely the
> class of silent traceability gap this release exists to close. Pass
> `--expect-version 1.1.0` explicitly as a second, independent guard.

## Known issues

### D2 — the score popup is never drawn

- **Severity:** medium. Cosmetic feedback, gameplay unaffected — but it
  removes the single most important moment-to-moment reward signal in a
  bubble shooter.
- **What a player sees:** popping bubbles never shows a score popup. The
  points you earned appear only in the HUD total.
- **Cause:** the ViewModel advances its FX clock with `_fxElapsedMs +=
  elapsed` where `elapsed` is the **Ticker's cumulative** duration, so the
  clock grows quadratically. Every popup is already expired by the time
  `bubble_renderer.dart` subtracts its *linear* `createdAt`. The popup
  **is** created, **is** in the list, and **is** retired on a correct
  schedule — only the paint is wrong. That is why a report of "the popup
  doesn't show up" does not reproduce without a tick rate and a tick count.
- **Status:** characterised in `docs/design/specs/honest-shot-score.md` §1.2
  and regression-probed in the
  [QE-10 template trial report][qe10-trial]. **The fix is not in this
  release** — nothing in the 12 commits touches the FX clock.
- **Ships in:** PB-01 (the honest shot score), blocked on the implementation
  issue being filed. See theme 10.

### D3 — particle bursts share D2's clock

The same quadratic-clock defect in a second place (`bubble_renderer.dart`),
found while characterising D2. Same fix scope, same release.

### Carried forward from v1.0.0

- No accessibility audit, performance budget, or cross-browser evidence
  (QE-3 #71, QE-4 #72, QE-5 #73).
- A player with the tab open can play a stale build for up to ten minutes
  with no reload prompt (#101, arising from QE-8's measurements).

## Rollback
